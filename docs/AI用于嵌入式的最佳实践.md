# AI 用于嵌入式开发的最佳实践（2026）

> 说明：题目里的"AI 用于嵌入式"其实包含三条独立但常被混谈的线，先分清再谈实践。
>
> | 方向 | 一句话定义 | 关键词 |
> |---|---|---|
> | **A. AI 作为开发助手** | 用 LLM/Agent 帮你写固件 | LLM、Agent、RAG、MCP |
> | **B. AI 跑在设备上** | 把模型塞进 MCU | TinyML、Edge AI、量化 |
> | **C. AI 作为产品能力** | 设备带生成式 AI 功能 | 端侧小模型、Function Calling |
>

## 一、AI 作为开发助手（AI for Firmware）

### 1. 上下文工程 —— 收益最大的一环

通用助手失败的首要原因是**看不到硬件事实**（`.ioc`、linker script、datasheet）。实践做法：

- **维护项目记忆文件**（`AGENTS.md` / `CLAUDE.md` / `.cursorrules`），至少写清：
  - MCU 型号/变体、时钟树、**Flash/RAM 上限**
  - 引脚映射、已占用的 I2C/SPI/UART 总线
  - **确切的构建命令**（`make`/`cmake` 参数、`arm-none-eabi-gcc` 版本）
  - 编码规范（MISRA 子集、禁用项：动态内存/递归/异常）
- **RAG 注入可信上下文**：datasheet、参考手册、SDK/HAL 文档、CubeMX 输出、linker script。目标是把输出**约束到真实存在的寄存器/宏/函数**，这是抑制幻觉最有效的手段。
- 把 datasheet PDF 直接纳入上下文，可支持离线（air-gapped）工作流。

### 2. 模型与工具选择

- **敏感固件优先本地模型**（Ollama / LM Studio 跑 DeepSeek-Coder、Qwen-Coder、Llama 变体）：避免 IP 外泄与遥测风险。
- 云端大模型用于**架构讨论、协议设计、文档**等非敏感任务。
- 用 **MCP（Model Context Protocol）** 把 LLM 接到 HAL、构建系统、串口、OpenOCD/调试器上，实现"读真实工程 → 改 → 编译 → 烧录"闭环，而不是靠粘贴代码。
- 关键：助手能否"看到"你的工程文件（`.ioc`、`.ld`、`stm32xxxx_hal_conf.h`）比模型本身多强更重要。

### 3. 任务分解：从低风险到高风险

**这是最重要的一条风险策略**，不要一上来就让 AI 写实时控制环路。

| 阶段 | 可交给 AI 的内容 | 风险 |
|---|---|---|
| 先做 | 外设初始化代码、驱动脚手架、调试桩、单元测试、Doxygen 文档 | 低 |
| 再做 | 状态机、协议解析、数据缓冲 | 中 |
| 最后 | ISR 时序、实时控制、安全/认证模块 | 高，必须人工主导 |

### 4. 提示与模板约束

- **模板化生成**：让 AI 只在预定义结构里填空 —— `main()` 主循环、ISR 骨架、驱动头文件、链接脚本。
- 强制约束显式写进提示：
  - 禁止动态内存分配、递归、异常处理、大型抽象
  - 静态缓冲区 + 中断驱动，替代"动态队列 + 回调"
  - 明确栈上限、执行周期预算
- 要求输出**可追溯**（注释引用手册章节/寄存器名），便于人工核对。

### 5. 验证闭环 —— 不可省略

生成代码必须过这道流水线才算数：

```
编译 → 静态分析(MISRA/Coverity/cppcheck) → 栈/内存占用分析
     → 单元测试(Unity/Ceedling) → HIL → 上板实测
```

- **人工必查四项**：寄存器地址、时钟树、引脚复用（AF）、时序序列。
- 用 **CI 门禁**（gated check-in）：静态分析 + 覆盖率不达标不允许合入。
- 反馈闭环（编译失败/静态告警回灌给模型）能持续提升生成质量，比一次性生成有效得多。

### 6. Human-in-the-Loop 审批闸门

- **烧录/擦除/flash 写地址必须人工确认** —— 错误的 `flash_write` 会直接让板子变砖，比 `rm -rf` 更严重。
- 用 git 分支 + 小步提交，保证任一步可回滚。
- 默认拒绝清单：屏蔽 `.env`、SSH 密钥、量产密钥等敏感文件。

### 7. 常见陷阱（务必知道）

| 陷阱 | 后果 |
|---|---|
| **寄存器/API 幻觉** | 生成同系列**不同变体**上不存在的 CMSIS 函数 |
| **资源假设错误** | 假设的堆大小导致 Cortex-M0 直接栈溢出 |
| **通用助手缺环境感知** | 看不到 `.ioc` / linker script，引脚冲突 |
| **非确定性代码** | 动态分配、递归 → 碎片化、栈深不可预测 |
| **忽略实时性** | 不感知中断延迟、jitter、优先级反转、竞态 |
| **遥测 / IP 泄露** | 专有固件上传云端（国防、医疗承包商尤其敏感） |
| **许可证风险** | 微调语料来自开源固件/SDK，输出可能有 IP 争议 |
| **行为验证鸿沟** | 代码"看起来对"，但闭环时序行为仍需硬件验证 |

### 8. RTOS 场景

- AI 适合**静态分析**：任务优先级、栈使用量、优先级反转、信号量死锁风险。
- 但结论必须用**真实 trace 验证**（SWO / SystemView / FreeRTOS trace），不能只信静态建议。

## 二、AI 跑在设备上（TinyML / Edge AI）

### 1. 先做可行性"六步评估"，再动手

| 步骤 | 内容 |
|---|---|
| 0 | 明确边界：模型类型、输入尺寸、类别数、推理频率、**延迟上限、功耗预算** |
| 1 | 工具初筛：Edge Impulse / STM32Cube.AI Profiling |
| 2 | **Flash 评估**：权重 + 运行时 + 算子库 + 预处理 + 固件 |
| 3 | **RAM 评估**：Tensor Arena、权重、预处理缓冲、堆栈 |
| 4 | **算力校验**：预处理 + 推理总时间 < 数据更新窗口 |
| 5 | **功耗评估**：算平均功耗，不是单次峰值 |
| 6 | 算子支持 + 集成可行性确认 |

### 2. 量化是核心环节

| 方式 | 内存 | 加速 | 精度损失 |
|---|---|---|---|
| FP32 | 4× | 1× | 0% |
| FP16 | 2× | ~1.5× | <0.5% |
| **INT8（推荐）** | **4× 压缩** | **2–4×** | **1–3%** |
| INT4 | 8× | 4–8× | 3–8% |

- `q = round(f / scale + zero_point)`
- **校准必须用真实传感器数据**，否则推理出 NaN。
- 精度敏感模型用 **QAT（量化感知训练）**，优于直接 PTQ。
- 其他压缩：剪枝（~3× 压缩）、知识蒸馏（<1% 损失）、低秩分解。

### 3. 硬件加速

- **CMSIS-NN**：Cortex-M 定点算子库，卷积可提速 ~3×（实测 ~12 万 → ~3.8 万周期）。
- **Helium/MVE**（Cortex-M55/M33）、**NPU**（STM32N6）、ESP32-S3 DSP 指令。
- 编译务必开：`-O2 -mfloat-abi=hard -mfpu=...`，否则加速不生效。

### 4. 内存治理（RAM 不足的头号解法）

- **Tensor Arena 精确调优**是核心手段。
- 用 `MicroMutableOpResolver<N>` **仅注册模型用到的算子**，替代 `AllOpsResolver`，大幅省 Flash/RAM。
- 流式预处理，避免大缓冲。
- STM32 上：`static uint8_t tensor_arena[N] __attribute__((aligned(16)));` + placement new。

### 5. 实时与功耗

- **双缓冲队列**解耦采集（中断）与推理（主循环）。
- 实时调度（`SCHED_FIFO`）只多 ~7% 功耗，但延迟可降低一个数量级。
- `I_avg = I_idle + (I_infer − I_idle) × t_infer / T_period`。

### 6. 工具链选择

| 工具 | 定位 |
|---|---|
| **TensorFlow Lite Micro** | 运行时仅 ~16KB，无 OS 依赖 |
| **STM32Cube.AI** | ST 官方，自动生成代码 + CMSIS-NN |
| **Edge Impulse** | 采集→训练→部署一站式 |
| **CMSIS-NN** | ARM Cortex-M 定点加速库 |
| ExecuTorch | PyTorch 生态端侧方案 |

### 7. 常见坑

| 症状 | 原因 | 解决 |
|---|---|---|
| `AllocateTensors() failed` | Arena 不足 | 增大 `kTensorArenaSize` |
| 推理 NaN | 校准数据不匹配 | 用真实传感器数据 |
| Flash 不足 | 注册了全部算子 | 仅注册所需算子 |
| 延迟过高 | 未启用 CMSIS-NN | 启用定点加速 |
| 精度骤降 | INT8 过激进 | 改混合量化 / QAT |
| DSP 未生效 | 编译未优化 | 加 `-O2 -mfloat-abi=hard` |

## 三、AI 作为产品能力（设备带生成式 AI）

- **端侧小模型（SLM）做意图识别/唤醒，云端大模型兜底**：兼顾延迟、成本、隐私。
- 用 **Function Calling / 规则引擎**约束输出，避免不可控的生成。
- 实时任务仍由确定性代码执行，AI 只做"上层决策"。
- 隐私敏感场景走全本地推理；算力敏感场景走联云。

## 四、浓缩成 8 条最佳实践

1. **上下文优先**：维护项目记忆文件 + RAG 注入 datasheet/SDK/linker script，比换更强的模型更有效。
2. **敏感代码用本地模型**，避免 IP 与遥测泄露。
3. **从低风险任务切入**：初始化代码、驱动脚手架、测试、文档 → 再逐步到 ISR、实时环路。
4. **强制约束写入提示**：无动态内存、无递归、确定性、固定栈。
5. **验证闭环不可省**：编译 + MISRA 静态分析 + 栈/内存分析 + 单元测试 + HIL + 上板。
6. **人工审批闸门**：烧录地址必须人工确认，git 小步提交可回滚。
7. **端侧 AI 先评估再动手**：六步法算清 Flash/RAM/算力/功耗；INT8 量化 + CMSIS-NN 是标配。
8. **区分三条线**：开发助手（写固件）、端侧推理（模型上 MCU）、产品 AI（生成式功能），三者的最佳实践并不通用。
