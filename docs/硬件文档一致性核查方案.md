# 阶段 0：上电前硬件文档一致性核查方案

> **场景**：手上有一块板子 + 原理图 + 一批器件文档，想在**开始写代码之前**让 AI 帮忙核实：
> 这些文档是不是都针对**当前这块板**？彼此之间有没有矛盾？
>
> **与原方案的关系**：`Win11-AI嵌入式工程落地方案.md` 是"代码层护栏"，本文件是它前面的"**文档层地基**"。
> 串联关系：**本文档 → `HARDWARE-TRUTH.md` → 回填 `AGENTS.md` §1 → 才能开始让 AI 写代码。**

---

## 0. 为什么必须单独做这一步

原方案有一个隐含假设：**`AGENTS.md` 第 1 节的硬件事实是正确的**。这个假设在你的场景下**不成立**，因为：

| 风险 | 后果 |
|---|---|
| 器件手册是**系列手册**而非具体型号手册 | 引脚表、外设数量部分对得上部分对不上，**错误极难发现** |
| 原理图 Rev C，BOM Rev B | 元件有增减，引脚映射漂移 |
| 原理图写 `STM32F407VGT6`，BOM 写 `STM32F407VET6` | Flash 差一倍、封装不同（LQFP100 vs 64） |
| 给的是隔壁型号板子的原理图 | 引脚、电源树全错 |
| I2C 开漏但无上拉 / LDO 电流不足 | 代码写完才发现硬件不工作 |

**最危险的不是"明显错"，而是"看起来对"。** 所以这一步的目标不是"读一遍文档"，而是
**把文档变成带出处的结构化事实表，并把矛盾点显式登记出来**。

---

## 1. 能力边界（先认清，否则会误判 AI 的结论）

### AI 能做

- ✅ **文档 ↔ 文档**的一致性核查（原理图 / BOM / 器件手册 / 板级规范 / 丝印图）
- ✅ 抽取结构化事实（电源树、时钟树、引脚映射、接口拓扑、特殊引脚）
- ✅ 找出矛盾点并按严重度分级
- ✅ 生成"待实物验证清单"（测什么、用什么仪器、期望值多少）

### AI 不能做（必须人来，AI 只能给清单）

- ❌ 判断**实物**与文档是否一致（丝印读数、通断、阻抗）
- ❌ 发现焊接 / 装配 / 元件错料
- ❌ 上电时序、纹波、EMC、热设计验证
- ❌ 替代万用表、示波器、逻辑分析仪

> **结论**：AI 交付的是「**文档一致性报告 + 待实物验证清单**」。
> **实物一致性的最终判定权永远在人。** 任何声称"AI 已验证过板子"的说法都是错的。

---

## 2. 核查流程（7 步）

```
Step 1  板卡身份指纹  ── 这块板到底是谁？（型号 / Rev / 日期 / MCU 丝印）
   ↓
Step 2  文档清单与覆盖检查 ── 该有的文档都有吗？（含"缺哪几页"）
   ↓
Step 3  结构化抽取  ── 从散乱 PDF 抽出 5 张可比对的表
   ↓
Step 4  交叉一致性核查 ── 原理图 ↔ BOM ↔ 手册 三方对照，找矛盾
   ↓
Step 5  冲突裁决与登记 ── 谁说了算？不一致点记入 CONFLICTS.md
   ↓
Step 6  待实物验证清单 ── AI 判不了的，转成可执行的测量任务
   ↓
Step 7  产出与回填  ── HARDWARE-TRUTH.md → 回填 AGENTS.md §1
```

**顺序不可跳**：没有 Step 1 的身份确认，Step 4 的对照毫无意义（可能整份文档都不属于这块板）。

---

## 3. Step 1：板卡身份指纹（Identity）

这是**整份方案的地基**。先确定"这块板是谁"，再谈其他。

### 3.1 实物侧（需要你提供清晰照片，或自己读）

| 项目 | 位置 | 记录内容 | 示例 |
|---|---|---|---|
| 板名与版本 | PCB 丝印（常见于板边或背面） | 完整型号 + Rev | `DEMO-F407-REV C` |
| PCB 生产日期 | 丝印或 `YYWW` 格式码 | 年月周 | `2435`（24 年第 35 周） |
| MCU 激光刻字 | 芯片顶面 | **完整型号 + 批次 + 产地** | `STM32F407VGT6` / `CHN 2437` |
| 晶振丝印 | 金属壳或旁边丝印 | 频率 + 负载电容 | `8.000MHZ` |
| 关键 IC 丝印 | 各 IC 顶面 | 型号（注意：可能是简化丝印码） | `AMS1117-3.3` |
| 连接器型号 | 器件本体 | 型号 + 针数 + 间距 | `XH2.54-4P` |

> **坑**：很多器件用**简化丝印码**（如 `LDO` 打 `662K`），必须查丝印码对照表才能反推型号。
> AI 猜丝印码的准确率很低，**这一项建议人工确认**。

### 3.2 文档侧（从原理图标题栏 Title Block 读）

| 字段 | 作用 |
|---|---|
| Project / Title | 工程名，应与板名对应 |
| Revision | 必须与 PCB 丝印 Rev **同号** |
| Date | 应**早于** PCB 生产日期（否则说明文档比板子新，可能不对应） |
| Sheet N of M | 总页数；**缺页是最常见的隐患** |
| Drawn / Checked / Approved | 有无审核痕迹（无审核的图可信度低） |

### 3.3 身份一致性判定

| 判定 | 条件 | 处理 |
|---|---|---|
| ✅ 一致 | 板名/Rev/日期 全部匹配 | 继续 |
| ⚠️ 疑似错配 | Rev 相同但日期晚于生产日期，或板名有细微差异（`REV C` vs `REV.C`） | 记入 `CONFLICTS.md`，人工确认 |
| ❌ 确认错配 | Rev 不同，或 MCU 型号不同，或板名完全不同 | **停止**，先要到正确的文档再继续 |

---

## 4. Step 2：文档清单与覆盖检查

### 4.1 必备文档清单

| # | 文档 | 缺失后果 | 你是否有 |
|---|---|---|---|
| 1 | 原理图 **全部 sheet**（含电源页、连接器页、丝印页） | 缺页 → 引脚/电源结论不可靠 | ☐ |
| 2 | BOM（含位号、型号、封装、厂商、替代料） | 无法做型号对照 | ☐ |
| 3 | **每个关键器件的「具体型号」手册** | 用系列手册 → 引脚/参数错 | ☐ |
| 4 | 板级规格（输入电压范围、接口电平、工作温度） | 无法判断供电/电平是否匹配 | ☐ |
| 5 | 官方 Errata / Release Note | 已知 silicon bug 无从知晓 | ☐ |
| 6 | 丝印图 / 装配图 | 无法核对位号与实物 | ☐ |

### 4.2 关键器件判定

以下器件**必须有具体型号手册**，缺一个就是一个 UNKNOWN：

- MCU / MPU
- 电源器件（LDO / DCDC）、电压基准
- 晶振 / 振荡器（要手册里的**负载电容与 ESR 要求**）
- 存储器（Flash / EEPROM / SDRAM）
- 所有 I2C / SPI 从设备（地址、时序、配置引脚）
- 通信收发器（CAN / RS485 / USB）
- 电平转换器（若有）

### 4.3 「系列手册 ≠ 型号手册」的判定方法

让 AI 执行这条检查，命中就要报 Critical：

```
对每份器件手册，回答三个问题：
1. 手册标题里的型号通配符是什么？（如 STM32F407xx / STM32F4 系列）
2. 这块板实际用的是哪个具体型号？
3. 手册中是否包含该具体型号的**独立引脚表 / 外设数量表**？

判定：
- 手册覆盖的是「整个系列、需按型号查表」→ 标记 WEAK（需逐条查表核对）
- 手册只覆盖系列级别、没有型号级差异说明 → 标记 MISMATCH（严重）
```

## 5. Step 3：结构化抽取（产出 5 张表）

> **关键原则**：不要让 AI「通读原理图」。让它**按 sheet、按字段**抽取，输出固定格式的表格。
> 每条记录必须带出处。

### 5.1 优先顺序：机器可读源文件 ≫ PDF ≫ 图片

| 输入形式 | 可靠性 | 说明 |
|---|---|---|
| **网表导出**（KiCad `.net` / Altium netlist / CSV） | ★★★★★ | 直接是 `网络名 ↔ 引脚` 的机器可读映射，**这是最优解** |
| **BOM 的 Excel/CSV 原件** | ★★★★★ | 位号 → 型号 → 封装，无需 OCR |
| 原理图 PDF（矢量） | ★★★☆ | 文本可提取，但网络标号顺序可能错乱，需按 sheet 分片 |
| 原理图 PDF（扫描件） | ★★☆ | 需 OCR，网络标号识别易错 |
| 原理图截图 / 照片 | ★☆ | 只能靠多模态模型读图，适合核对局部（如 MCU 周边、电源段） |

**行动建议**：如果你能拿到**网表**或**BOM 原件**，一致性核查的可靠性会高一个数量级。
PDF 图只是最后手段。

### 5.2 表 1：电源树 Power Tree

| 字段 | 说明 | 出处标注 |
|---|---|---|
| 域名称 | 如 `+3V3` `+5V` `VDD_MCU` | 页码 + 网络标号 |
| 来源 | 来自哪个器件/哪个输入 | 页码 + 位号 |
| 生成器件型号 | LDO/DCDC 具体型号 | 页码 + 位号 |
| 输入范围 | 电压范围 | 页码 / 手册章节 |
| 额定输出 | 电压 + **最大电流** | 手册章节 |
| 负载清单 | 该域下挂了哪些器件 | 页码 + 位号列表 |
| 负载总电流估算 | MCU + 各外设的峰值和 | 由手册汇总 |
| **裕量判定** | 额定输出 vs 负载总电流 | — |

**必查**：每个电源域的 `额定电流 ≥ 负载峰值 × 1.3`。不足即 Critical。

### 5.3 表 2：时钟树 Clock Tree

| 字段 | 说明 |
|---|---|
| 时钟名 | HSE / LSE / 内部 |
| 频率 | 如 `8.000 MHz` |
| 器件位号 | 晶振位号 |
| 负载电容 | 原理图上的 C 值 |
| **手册要求的 CL** | 晶振手册中 `CL` 标称值 |
| 匹配判定 | `原理图负载电容（含寄生）≈ 2×(CL − Cstray)` |
| 串联电阻 | 有无、阻值 |
| 接法 | 是否接在正确的 OSC 引脚（HSE_IN/OUT） |

**必查**：
1. 频率是否在 MCU 的 PLL 输入范围内
2. 负载电容是否与晶振手册要求匹配（**这是最常被忽略的坑**）
3. 晶振是否被接在错误的引脚（如把 HSE 接到 OSC32）

### 5.4 表 3：MCU 引脚映射 Pin Map（最核心）

| 字段 | 说明 |
|---|---|
| 引脚号 | 封装物理引脚号 |
| 引脚名 | 如 `PB6` |
| 网络名 | 原理图网络标号 |
| 功能 | GPIO / I2C1_SCL / SPI1_SCK ... |
| **AF 编号** | 复用功能编号（必须查手册 AF 表） |
| 方向 | 输入/输出/双向 |
| 上下拉 | 内部/外部，阻值 |
| 外部器件 | 接了什么 |
| **冲突检查** | 是否与 AF 表、其他功能冲突 |

**必查**：
- 每个外设功能在**该具体型号**上是否存在（系列手册常有不存在的组合）
- AF 编号是否与手册一致
- 是否有引脚被重复分配

### 5.5 表 4：接口映射 Interface Map

| 接口 | 必查项 |
|---|---|
| **I2C** | 从设备型号、7bit 地址、**地址是否冲突**、上拉阻值、总容性负载、电平 |
| **SPI** | 片选（硬件 NSS 还是软件 GPIO）、Mode、最高速率、多从机片选是否独立 |
| **UART** | 波特率、流控、电平（TTL/RS232/RS485）、有无收发器 |
| **CAN** | 收发器型号、终端电阻（**两端各 120Ω，板上是否已装**） |
| **USB** | 上拉电阻（D+ 1.5kΩ 或 D- 1.5kΩ 指示速率）、ESD、VBUS 检测 |
| **SDIO/ETH** | 上拉/下拉、阻抗、时钟走线要求 |

### 5.6 表 5：特殊引脚 Strapping & Critical Pins

| 引脚 | 为什么关键 | 必须确认 |
|---|---|---|
| `BOOT0` | 启动模式 | 有下拉电阻？悬空会导致偶发错误启动 |
| `NRST` | 复位 | 有 RC 滤波？复位按键？ |
| `SWDIO` / `SWCLK` | 调试 | **是否被当成普通 GPIO 用**（会锁死调试） |
| `VBAT` | RTC 备份 | 接电池还是接 VDD？悬空？ |
| `VCAP` / `VREF+` | 内核稳压/基准 | 电容值是否符合手册要求 |
| `PH0/PH1` (HSE) | 时钟 | 同 §5.3 |
| 器件 ADDR/SET 引脚 | I2C 地址选择 | 是否悬空（悬空=地址不确定） |
| `nWAKE` / `EN` | 电源时序 | 上电顺序是否正确 |

## 6. Step 4：交叉一致性核查（核心）

对每一条事实，做**三方对照**：

```
       原理图  ←→  BOM
         ↕           ↕
         器件手册 ←→ 板级规格
```

### 6.1 判定矩阵（每格必须有证据）

| 检查项 | 原理图 | BOM | 器件手册 | 判定 | 证据 |
|---|---|---|---|---|---|
| MCU 型号 | `STM32F407VGT6` @U1 p.3 | `STM32F407VGT6` | `STM32F407xx DS` | ✅ 一致 | sch p.3 U1 / BOM row 12 |
| MCU 封装 | LQFP100 | LQFP100 | LQFP100 | ✅ 一致 | … |
| Flash 容量 | 由型号推 1MB | — | 手册 Table 2 | ✅ 一致 | … |
| HSE 频率 | 8 MHz @X1 | `8.000MHz` | 手册 PLL 输入 4–26MHz | ✅ 一致 | … |
| 晶振负载电容 | C31=C32=20pF | `20pF` | 手册 CL=10pF | ⚠️ **需核算** | … |
| I2C 上拉 | 无 | 无 | 开漏需上拉 | ❌ **缺失** | sch p.5 |
| I2C 地址 | 传感器 A0 悬空 | — | 悬空=不确定 | ❌ **Critical** | … |

### 6.2 典型不一致清单（14 类，逐项过一遍）

| # | 类型 | 示例 | 严重度 |
|---|---|---|---|
| 1 | **版本错配** | 原理图 Rev C，BOM Rev B（元件有增减） | Blocker |
| 2 | **型号错配** | 图写 `...VGT6`，BOM 写 `...VET6` | Blocker |
| 3 | **系列手册代替型号手册** | 只有 STM32F4 系列手册，无型号级引脚表 | Critical |
| 4 | **封装错配** | BOM 封装 LQFP100，实物/图 LQFP64 | Blocker |
| 5 | **引脚功能错配** | 图把 PB6 接 I2C1_SCL，文档说 I2C2 | Critical |
| 6 | **电平错配** | 3.3V MCU 直连 5V 器件，无电平转换 | Critical（会烧板） |
| 7 | **上拉缺失** | I2C/CAN/USB 需要上拉但图上没有 | Critical |
| 8 | **电源能力不足** | LDO 额定 300mA，负载峰值 500mA | Critical |
| 9 | **时钟超范围 / 负载电容不符** | HSE 频率超出 PLL 输入范围；CL 不匹配 | Critical |
| 10 | **地址冲突** | 两个 I2C 从设备地址相同 | Major |
| 11 | **配置引脚悬空** | BOOT0 / 器件 ADDR 引脚未处理 | Critical |
| 12 | **调试/复位引脚被占用** | SWDIO 被当 GPIO | Major |
| 13 | **终端电阻缺失/重复** | CAN 板上无 120Ω，或两端都装了导致 60Ω | Major |
| 14 | **文档缺页** | Sheet 3 of 5 缺失 | Blocker |

### 6.3 严重度定义

| 级别 | 含义 | 处理 |
|---|---|---|
| **Blocker** | 无法开始开发（文档缺失/版本错配） | 必须解决后才能进入编码 |
| **Critical** | 会导致烧板、不工作、必须改硬件 | 必须实物确认 + 修板或改设计 |
| **Major** | 会导致返工、需要软件规避 | 记录，软件侧做规避 |
| **Minor** | 需要记录但不阻塞 | 记录到 `open-questions.md` |
| **Info** | 观察到的现象 | 记录即可 |

## 7. Step 5：冲突裁决与登记

### 7.1 裁决优先级（高 → 低）

| 优先级 | 来源 | 说明 |
|---|---|---|
| 1 | **实物实测** | 万用表/示波器量出来的。**最高**，但要排除测量误差 |
| 2 | 板卡官方 Errata / Release Note | 厂商官方勘误，明确说明"图错了" |
| 3 | **最新版原理图** | 注意是"最新 Rev"，不是"你手上那份" |
| 4 | BOM | 采购清单，通常跟随最新生产批次 |
| 5 | **具体型号**器件手册 | 手册是权威，但可能对应的是另一批次的物料 |
| 6 | 系列手册 / 网络资料 / AI 常识 | **最低**，不可作为裁决依据 |

### 7.2 登记格式：`CONFLICTS.md`

```markdown
## 冲突 #003：HSE 晶振负载电容不匹配

| 项 | 内容 |
|---|---|
| 严重度 | Critical |
| 检查项 | 时钟树 - 负载电容 |
| 原理图说 | C31 = C32 = 20pF（sch p.3，X1 周边） |
| 器件手册说 | 晶振 X1 要求 CL = 10pF（X1 手册 Table 3，p.7） |
| BOM 说 | 20pF（BOM row 88） |
| 判定 | **确认不一致** |
| 依据 | 两侧均有明确出处；按公式 C_load ≈ 2×(CL − Cstray) ≈ 2×(10−3) = 14pF，20pF 偏大 |
| 裁决 | 未裁决 —— 需实物测量 |
| 待验证 | 用 LCR 表量 C31/C32 实际值；或查晶振实测频偏 |
| 影响 | 时钟频偏 → UART 波特率误差 → 通信异常 |
| 状态 | OPEN |
```

### 7.3 状态机

```
OPEN → （人工确认后）→ RESOLVED-图错 / RESOLVED-手册错 / RESOLVED-实物错 / DEFERRED（暂不影响开发）
```

**禁止 AI 自行把状态改为 RESOLVED。** 只有人工确认才能关闭。

## 8. Step 6：待实物验证清单

AI 判不了的，转成**可执行的测量任务**：

```markdown
## 待验证 #V-001：3.3V 电源实际输出

| 项 | 内容 |
|---|---|
| 目的 | 确认 U2 (AMS1117-3.3) 实际输出是否满足负载需求 |
| 仪器 | 万用表（电压）+ 电子负载或示波器（纹波） |
| 测点 | C10 两端（+3V3 与 GND） |
| 条件 | 板上所有外设使能，MCU 跑满载程序 |
| 期望值 | 3.30V ± 3%（3.20–3.40V）；纹波 < 50mVpp |
| 判据 | 超范围 → 记录并评估是否更换 LDO |
| 关联冲突 | #005 |
```

**要求**：每条必须有「仪器 + 测点 + 条件 + 期望值 + 判据」。缺任一项的清单是无效的。

## 10. 防幻觉规范（本方案最关键的一节）

> 这一步的失败模式不是"AI 答不出来"，而是"**AI 自信地编造了一个看起来合理的器件参数**"。

### 10.1 强制引用格式

每条结论必须是三元组：**值 + 出处 + 置信度**

```
❌ 错误：AMS1117 最大输出电流是 1A
✅ 正确：U2 = AMS1117-3.3，最大输出 1A（出处：AMS1117 DS Rev.1.2 p.1 电气特性表，
       置信度 HIGH；BOM row 25 确认型号为 AMS1117-3.3）
```

### 10.2 `UNKNOWN` 是一等公民

明确要求 AI：**文档里没写的，就写 `UNKNOWN`，不许用先验知识补全。**
并在提示词里给出明确授权：

```
你有权限说 UNKNOWN。事实上，说 UNKNOWN 比给出一个未经证实的值更有价值。
任何未经文档证实的数值，都比 UNKNOWN 更糟糕，因为它会被下游当成事实使用。
```

### 10.3 双通道反查（治幻觉的核心手段）

**让 AI 先抽取，再让它"反查出处"**：

1. **通道 1（抽取）**：让 AI 从文档抽取出事实表
2. **通道 2（反查）**：**新开一个会话**，把通道 1 的结论列表给它，只问一个问题：
   「这个值在哪个文件、哪一页、哪个位号/图号能查到？」

判定：
- 找不到确切出处 → `NO-EVIDENCE` → **该结论是幻觉，必须删除**
- 只找到近似出处 → `WEAK-EVIDENCE` → 降级为 MEDIUM，人工复核
- 找到确切出处 → 保留

> 这一步能筛掉绝大多数"看起来对"的编造。**不要跳过。**

### 10.4 数值原样摘录

```
禁止：单位换算（mV↔V）、四舍五入、百分比转小数
要求：原样摘录，并标注原文单位
      原理图写 "4.7K" → 记 "4.7K"（不要写 4700Ω）
```

理由：换算和取整会引入"看起来合理但不精确"的值，且失去与原文的可对照性。

### 10.5 分片而非通读

| 反模式 | 正确做法 |
|---|---|
| 把 1000 页手册整个喂进去 | 按章节分片，只喂相关章节（如"电气特性"、"引脚定义"） |
| 让 AI "通读原理图，告诉我有什么问题" | 按 sheet 分片，按 §5 的字段逐项抽取 |
| 一次问"这块板对不对" | 拆成 §6.2 的 14 类具体检查项，逐项过 |
| 只喂手册不喂原理图 | 必须两方都给，否则无法对照 |

### 10.6 明确禁止的推断

在每次提示词里都带上：

```
禁止以下行为：
1. 用你的先验知识补全文档中未出现的器件参数
2. 假设"同类器件的常见做法"就是本板做法
3. 把系列手册的内容当成具体型号的结论（除手册明确说明型号无差异）
4. 为找不到出处的结论编造一个出处
5. 把"看起来合理"当作"已确认"
6. 在证据不足时给出倾向性结论（应写"无法判断"）
```

## 13. 反模式速查（这些做法会失败）

| 反模式 | 为什么失败 | 正确做法 |
|---|---|---|
| 直接问"这块板有什么问题" | 问题太泛，AI 会给一堆泛泛之谈 | 拆成 §6.2 的 14 类逐项过 |
| 把整本手册喂进去 | 上下文爆炸，抓错重点，还容易串章节 | 按章节分片 |
| 用系列手册代替型号手册 | 引脚表部分对得上，错误极难发现 | 先做 §4.3 的手册类型判定 |
| 只信 AI 给的器件参数 | 会编造看起来合理的数值 | 强制出处 + 双通道反查 |
| 让 AI 判断"实物是否一致" | AI 看不到实物 | 转成待验证清单，人来做 |
| 忽略"文档缺页" | 缺的那页往往就是电源或时钟 | Step 2 强制核对 `Sheet N of M` |
| 不做身份确认就开始对照 | 可能整份文档都不属于这块板 | Step 1 必须最先做 |
| AI 把冲突标为已解决 | 未经实物验证的"解决"是假象 | 状态只能由人工关闭 |
